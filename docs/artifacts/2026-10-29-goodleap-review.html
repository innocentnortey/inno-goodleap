Becomes finance.test.ts. This is the "what would my payment be" answer the contractor needs in 30 seconds; it is pure code, no model.

Input

  • Priority: lower monthly payment
  • Catalog 2026-10-29
→

Output (ranked by monthly)

HP-1 · Orchestration: where the model has autonomy and where it doesn't Recommend B

Where this comes up in the project

Every screen. The contractor enters $30,000. The homeowner asks about a promo. The contractor uploads an estimate. The homeowner verifies income. At each step someone had to decide: does code do this, or does a model? The brief grades "the quality of the conversational UX" and "AI Ecosystem Fluency". You rejected "just another chatbot" (D-11). The CTO wants nothing operationally fragile: "Don't give me a science project." Those three pulls meet here.

The problem we're solving

Decide, per step, whether the model drives or code drives. Example: the contractor's $30,000 quote → six payment figures. A chat agent would take seconds and could misstate a number; a button and a formula answer at once and are always right. But SCR-2's "what if I don't pay it off in 18 months?" is open-ended; a template cannot answer every phrasing.

Why it's hard

Too little AI reads as a calculator. That fails "conversational UX" and the guardrail requirement (the brief wants to see one). Too much AI reads as risk and slowness. Every borrower message then needs guarding (C-1, C-2), and the demo gets slower than buttons for simple choices. The agentic feature you asked for (D-5) must show real agent behaviour without handing navigation to a model.

Why we're asking you, and what your answer changes

Option B is what tonight's build follows, because your standing answers (D-5, D-11) point at it. You are asked to keep or overturn it, not to unblock the build. Picking A means a chat agent drives the journey and Foundation's screen skeleton is reworked. Picking C removes the question box and the explanation text, and leaves extraction as the only model call, which weakens the "conversational UX" answer in the interview.

A · Chat copilot runs the journey

One agent with tools drives every step. Easy to demo. Slow for decisions; every borrower message needs guarding; this is the thing you objected to.

B · Fixed skeleton, AI at the seams Recommended

Screens and transitions are code. The model is called at SCR-2 (the question), SCR-3 (extraction inside a bounded 6-step agent) and SCR-4 (the exception explanation). Each AI moment has a clear "why AI here". GP-72: draw the skeleton yourself; autonomy only where the path can't be known.

C · No generated text

Extraction only; templates everywhere. Safest. Weak on "conversational UX" and the guardrail requirement.

If you pick differently: A reworks Foundation's shell into an agent-driven flow and adds guarding to every message; C deletes SCR-2's model call and SCR-4's explanation, and the interview answer "why AI here and not there" loses its two best examples.

Success measure: a reviewer can name, for each screen, why AI is or isn't there; the agent trace never exceeds 6 steps. Evidence: WP-1 (no model needed), WP-2 and WP-3 (model needed).

HP-2 · Guardrails that make borrower-facing text safe Recommend the code chain

Where this comes up in the project

SCR-2 and SCR-4: the only two places a model writes words a borrower reads. The homeowner asks "what happens if I don't pay it off in 18 months?" and the answer must carry the right numbers, no reassurance, and the TILA/RESPA disclosures (the truth-in-lending lines: APR, term, total cost of credit). The brief's hard line is "No AI system can make or imply a credit decision", and the Head of Compliance wants to "see exactly what the system said and why". WP-2 surfaced this.

The problem we're solving

Make every model answer safe to show, and provable afterwards. Example input: the model writes "You'd pay about $1,500 a month for 18 months." Required output: that text is blocked, because $1,500 is not one of the numbers code computed ($1,666.67 is), the model is asked once more with the reason, and if it fails again a safe template is shown. Every attempt is written to the audit log.

Why it's hard

A language model paraphrases numbers ("about fifteen hundred"). It slips into reassurance ("you should be fine"), which is an implied credit decision (C-1). Prompt instructions alone fail silently. They leave nothing to show Compliance (C-5). A second-model classifier catches subtler phrasing but adds a call and latency against the 5-second target. The blocked-phrase list is a known limit: it catches the words we thought of.

Why we're asking you, and what your answer changes

Segment B builds the code chain tonight because it is deterministic and cheap. You are asked whether that is enough for the demo, and whether the classifier belongs on the roadmap page (SCR-7) as v2 or in tonight's build. Adding the classifier now costs another model call per answer and a second prompt to write; leaving it to v2 keeps latency low and gives the design doc an honest "known limit" to defend.

Prompt instructions only

Fails silently; nothing to show Compliance.

Code checks, in order Recommended

Number check → approval-language rules (words like "you qualify", "guaranteed", "no risk" and the rest of the list) → disclosures attached by code. Regenerate once with the reason, then the safe template. Every outcome logged. Deterministic, explainable, cheap.

Add a second-model classifier

Better recall on subtle implied approval. Another call, more latency. Named as v2 on SCR-7.

If you pick differently: adding the classifier tonight means a second prompt, a second call per answer and a latency hit against the 5-second target; dropping to prompt-only means the brief's "at least one guardrail" has nothing checkable behind it.

Success measure: guardrail-check.ts blocks all ≈10 crafted outputs; zero shown records contain an approval phrase or a number outside the allowed set. Evidence: WP-2.

HP-4 · Extraction that never guesses Recommend schema + code validation

Where this comes up in the project

SCR-3. The contractor uploads roof_messy.txt, a real-shaped estimate with line items, "30 sq", a deposit written as "(2,000)" and "BAL DUE 28,000". The application-prep agent must turn it into prefilled fields so nobody retypes it. The brief says staff "extract key details by hand" today, and estimates differ across 15,000 contractors. WP-3 surfaced the exact failure shapes.

The problem we're solving

Read a messy document into typed fields without ever inventing a value. Input: hvac_missing_total.txt, which has no total. Required output: estimateTotal stays blank and is marked needs_input. The reason shown is the estimate's own note that pricing waits on an attic inspection. The checklist tells the contractor to ask for the finished total. Never a plausible number.

Why it's hard

Messy text invites guessing. A model may read "(2,000)" as a line item, not a deposit. It may fill a missing total from the line items. A wrong amount in a loan application is worse than a blank (R-7: nothing is guessed silently). Derived values such as the financed amount must come from code, not the model (C-3), and each field needs a source quote so a reviewer can check it.

Why we're asking you, and what your answer changes

Segment C builds this tonight as recommended. You are asked to keep it, or to change the thresholds and statuses. A looser rule (accept low-confidence values as ready) makes the demo look smoother but breaks "never guess"; a stricter one (everything needs_review) makes the prefill look useless. The confidence threshold itself is set in code and can move after your review.

Tool-use with a JSON schema, code validates Recommended

Every field carries a source quote and a confidence. Code validates ranges and computes derived values. Below threshold → needs_review; missing → needs_input.

Free-text extraction, model fills everything

Fewer blanks on screen; no source quotes; the model may invent a total. Breaks R-7.

If you pick differently: loosening the statuses changes what SCR-3 and SCR-5 show as blank and what the Playwright check expects for the HVAC estimate.

Success measure: WP-3's three estimates behave as specified; the HVAC estimate yields no invented total.
